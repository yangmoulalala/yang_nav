## 结论与证据边界

用户两轮手动运行都已证实定位后端输出发生大修正。最新一轮 00:26:41.803 接收 map (8.56,-3.48)，00:27:27.160 报告成功。00:27:10.787 恢复修正 1.19752 m / 1.34399°，相邻约 0.18 s 真值仅移动 0.01964 m；00:27:12.982 再修正 0.959883 m / 3.58724°，相邻真值完全静止。因此问题确实重复发生，RViz 跳变有真实定位输出依据。

目前不能把初始误差直接定责为前端 LIO 不稳。两轮手动文本日志都缺少原始 odometry 和完整 TF 时间序列，只有后端恢复量，无法判断是原始里程计先偏、后端匹配先偏，还是二者间的时间/参考关系出错。

本次新增了四轮独立诊断测试。三轮真实 Nav2 测试都被洞前障碍检查拦住，未到出口故障段，不能算该问题的有效否定复现。一次物理路线隔离回放完成了洞口、出口后行驶和转弯；该轮原始 LIO 相对真值的位置误差最大 0.14904 m、yaw 最大 0.66269°，全局定位误差最大 0.23767 m，全程 NORMAL，没有米级跳变。这说明这条路段在所测条件下并非必然使 LIO 发散，但不能据此排除用户真实故障中的前端异常。

两次手动故障前均有启动期 IMU gap 和重新初始化，新三轮无故障基线没有 IMU gap。已补测静止 cold reset，但那轮未走到洞后，不能验证或排除“重新初始化相关”假设，更不能把启动时重置直接写成已确认根因。

完整路线隔离回放中出现 7 帧 `lidar_updated=false`、matches=0、输出 cloud 为空，同时没有米级发散。这给旧合并警告提供了空点云这一具体线索，但本身不能说明所有 invalid observation 都是同一原因，也不能把该警告直接等同于漂移根因。

## 已补齐后续手动运行的取证

- 新 `tools/nav_regress/record_localization.py` 是独立只读记录节点，记录原始前端帧/预测、前端 session/epoch、MID360 IMU、全局 odometry、map→lio_odom / lio_odom→base_link TF、状态、速度和 Gazebo 真值；保留仿真消息时间、接收仿真时间及单调接收时间。没有向导航/定位反馈数据。
- `run_nav.sh` 新增 `LOC_REC=true` 可选开关，在定位启动前开始记录，进程纳入原有本轮进程组清理。
- `sim_rviz.sh` 默认启用该开关；`LOC_REC=false` 可关闭。沿用手动入口启动即可，不需要另开记录器。
- 输出 `OUT/localization_trace.jsonl`；如同名文件已存在，新建带时间戳的文件，避免多次手动运行相互覆盖。
- 只保存前端点云标量元数据，不保存原始点云；本记录足以比较“哪条位姿链先偏”，不能替代完整雷达/IMU rosbag 的匹配器离线重放。
- 三轮以上真实中间件记录已用于上述分析；最终正式记录器另经隔离 ROS/Gazebo 发布器冒烟测试：502 条记录，包含 frontend_frame / imu / truth，正常 SIGINT 退出，旧文件保留。Python 编译和 shell 语法检查通过。没有跑与记录器无关的导航单元回归。

后续复现应先比较同一时刻的 lio_odom→base_link 与真值，再看 map→lio_odom 是否先出现异常修正；这能将前端里程计故障与后端全局匹配/恢复故障分开。初始偏差原因尚待带新记录的故障轮次确认。

本次未修改 `src/z-localization` 的实现或参数，没有在导航中加入定位过滤、平滑或纠正；新增内容仅为诊断工具、启动记录开关和证据报告。测试全部已结束，未保留仿真后台进程。
