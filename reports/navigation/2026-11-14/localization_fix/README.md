# 出洞定位漂移修复与自主验证（2026-11-14）

> 归档说明（2026-11-14）：本目录保留结论、脚本和精简证据。大型原始数据已转入本机 `backup/report-evidence-2026-11-14.tar.zst`，源码快照、编译产物和重复中间记录已清理；清单与恢复方法见 `reports/maintenance/2026-11-14/commit_cleanup/README.md`（路径均从仓库根目录解析）。下文的 before/after、trace 和输入文件路径按原实验记录保留，现存状态以清单为准。

已修复前端瞬时扫描调度、仿真陀螺仪方差配置和后端 SUSPECT 恢复丢弃连续航向三个问题，并完成编译、全部前后端测试、相同传感器输入的消融回放及两轮物理过洞。两轮均未出现先前手动运行的米级漂移或大角度恢复航向错误；第二轮出洞后由真实 Nav2 完成两个后续目标。

**验收边界：** 原手动故障没有保存原始点云，不能精确重放当时 1.76 m 的前端漂移。完整 Nav2 从出生点开始的 `fixed_nav1` 仍被洞前障碍检查拦住；本报告通过物理路线夹具覆盖出洞定位故障段，没有把洞前超时记作验证成功。该停车问题仍需独立处理，整套自主导航全流程尚未验收通过。

## 依据与修复

原始故障证据在 `../manual_repeat_0054/`。其中原始 `lio_odom→base_link` 最大位置误差 1.76441 m、yaw 误差 8.57478°；后端恢复后全局真实 yaw 误差达到 26.8479°。运动阶段没有 IMU-gap 重置，外参保持恒定。应区分原始 LIO 漂移与后端增加的错误航向。

用户本轮明确要求“修复这个问题，并自己测试”，据此修改定位端。导航继续直接使用定位输出，没有在导航端过滤、校验或修正位姿。

### 瞬时扫描按真实采集时刻更新

`frontend/src/input.cpp` 的 `Input::nextEnd` 现对首尾时间相同的扫描，在 IMU 覆盖到该扫描时刻后直接选择真实采集端点。连续扫描原有分段调度保留。

Gazebo GPU 雷达整帧点云同一时刻采集。旧调度沿用连续扫描窗口端点，会等后续数据、产生无证据的外推，窗口落在扫描间隙时还有空更新。相同输入对照中，旧版分别有 6 / 9 帧未进行激光更新，修复后均为 0。

单独此修改对路线误差只小幅改善，不能据此认定它单独解释原手动运行 1.76 m 的漂移。

### 仿真角速度采样方差与传感器模型一致

仅修改 `bringup/config/sim/frontend.yaml`：`filter.gyro_variance` 从 `0.25` 改为 `0.000004`。

`sentry_gazebo/sdf_builder.py::imu_xml` 的角速度噪声标准差为 `2e-3 rad/s`，其方差为 `4e-6`。前端 `ImuNoise::varianceRates` 按原始 IMU 区间将采样方差转换为传播预算，参数语义一致。旧值是模拟传感器白噪声方差的 62500 倍，削弱惯性航向约束，使局部几何匹配容易拉偏姿态。

未缩小加速度有效方差：另一次将其直接设成模拟白噪声方差 `4e-4` 的实验，路线位置误差反而达到 2.84 m，已放弃。物理接触和离散仿真误差需要有效噪声余量。真车配置及启动阶段参数未改。

### SUSPECT 的 UWB 恢复先验证同代次连续航向

`backend/src/localization_recovery.cpp::makeUwbRecoveryPriorLocked` 现仅在 SUSPECT、存在可信姿态且 epoch 一致时，使用最后可信 map 变换结合当前里程计前推的航向作为恢复初猜。

UWB 提供位置约束，不能直接测量航向。此前恢复每次先丢弃连续航向、全圈搜索，在相似洞口几何中可能选择错误姿态。现在先验证连续航向；几何验证失败仍可全圈搜索。LOST 和跨 epoch 仍采用原全圈恢复，不将旧代次姿态作为新初猜，也没有硬性限制航向或平滑恢复输出。

- 前后端全部 **20 个 CTest 测试组通过**，XML 内共 **181 个测试用例，0 失败、0 错误**，见 `tests_full.log`、`test_results_*.log`、`verification.json`。
- 新前端 3 个用例覆盖：瞬时扫描不等待下一帧、扫描间隙不产生空更新、连续扫描保持有界窗口。
- 新后端集成用例通过真实匹配器验证：非零连续航向下，位置偏差经 UWB 恢复后回到正确姿态。将实现临时换成修复前版本时该用例失败；恢复修复版后通过，见 `backend_regression_before_test.log`、`backend_test_final.log`。测试期间安装的仿真节点未被替换为旧版本。
- 原有跨代次边界、LOST、恢复、ROS 接口及匹配测试全部通过。

`colcon test-result` 同时计入 CTest 外层条目和用例 XML，因此其汇总为 201；181 是 `test_results` 中实际 `<testcase>` 的数量。

### 相同传感器输入回放

### 修复后两轮真实物理过洞

开启 Gazebo GUI、RViz、双雷达、UWB、真实碰撞与惯性传感器，静止执行 coordinated cold reset 后行驶。测试夹具只用 Gazebo 真值反馈驱动底盘跟随原手动参考路线，不瞬移、不伪造传感器，也不将真值注入定位器。路线阶段停止 Nav2 控制进程，因而不是原手动运行控制输入与进程负载的精确重演。

两轮真值都穿过 tunnel_3 约 0.355 m 深的洞体，洞体内各有 40 个真值样本，见 `physical_route_coverage.png` 与 `verification.json`。路线参考时长 72.928 s，实际物理执行约 74 s。

### 完整 Nav2 洞前停车：仍未通过

`baseline1`、`fixed_nav1` 从出生点由完整 Nav2 驱动到原目标，仍在洞前停车；后者约 100 s 超时，未覆盖出洞段。记录到了洞口通道内约 map `(5.075,-4.975)` 的孤立 lethal 格，位于计划经过的 padded footprint 边缘内，前方障碍检查因此拦停。静态图、动态标记及地形投影各自的贡献尚未最终区分，不能直接删障碍或关闭碰撞检查。

该现象与本次定位修复的出洞漂移验证独立；本轮没有改导航、代价地图、雷达障碍过滤或碰撞阈值。完整自主过洞仍待解决这个障碍来源问题。

`baseline_commands` 为环境临时无效 ROS 包名错误导致的启动失败，不计有效仿真；最早尝试 rosbag 录制时环境没有 `ros2 bag`，随后改为独立二进制输入记录器，均保留原失败日志。
